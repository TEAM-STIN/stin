# 테스트 기준

**구현한 기능에는 테스트를 쓴다. 건너뛸 수 없다.**

테스트의 목적은 커버리지 숫자가 아니라 **검증 가능한 하드 시그널**이다.
에이전트든 사람이든, 테스트가 통과하지 않으면 "됐다"고 말할 수 없어야 한다.

## 무엇을 테스트하나

| 작업 종류 | 반드시 담을 것 |
|---|---|
| 새 기능 | 정상 동작 + 엣지 케이스 + 경계값 |
| 버그 수정 | **재현 테스트를 먼저 쓴다.** 실패를 확인하고 → 고치고 → 통과시킨다 |
| 리팩터링 | 기존 동작이 보존되는지. 테스트를 고쳐야 한다면 리팩터링이 아니다 |

## 반드시 테스트하는 영역

- **추천 엔진** — 단계 구성, 후보 필터링, 조합 생성
- **성분 병용 규칙 검증** — `BLOCK` / `WARN` 판정, 시간대 분리로 해소되는 경우
- **트레이드오프 처리** — 해가 없을 때 조건 완화 순서
- 경계에서의 파싱 (잘못된 입력이 제대로 거부되는지)

이 영역들은 로직이 데이터에 의존해서 눈으로 검증하기 어렵다. 요구사항은
[requirements.md](requirements.md), 성분 근거는
[functional-ingredients.md](functional-ingredients.md).

## 테스트하지 않아도 되는 것

- 순수한 스타일·문구 변경
- 자동 생성 코드 (Prisma Client, shadcn 원본)
- 프레임워크가 이미 보장하는 것 (Next.js 라우팅 자체)
- 설정 파일

## 러너

| 대상 | 러너 | 위치 |
|---|---|---|
| `apps/api` | Jest | `src/**/*.spec.ts` |
| `apps/api` E2E | Jest | `test/*.e2e-spec.ts` |
| `apps/web` | Vitest + Testing Library | 컴포넌트 옆 `*.test.tsx` |

> `apps/web`의 Vitest는 아직 도입 전이다 —
> [exec-plans/active/001-harness-engineering.md](exec-plans/active/001-harness-engineering.md) Phase 2.

## 작성 방침

- **테스트 이름은 한국어로 무엇을 검증하는지 쓴다.**
  `it('레티놀과 AHA를 같이 넣으면 BLOCK 판정이 나온다')`
- 하나의 테스트는 하나만 검증한다
- 픽스처는 테스트 파일 안에서 자기완결적으로. 다른 테스트의 상태에 의존하지 않는다
- 실패 메시지만 보고 원인을 알 수 있게 쓴다

## 미결

`apps/api` 테스트가 실제 DB를 쓸지(테스트 컨테이너) 목을 쓸지 아직 정하지 않았다.
추천 엔진 구현을 시작할 때 결정하고 이 문서에 적는다.

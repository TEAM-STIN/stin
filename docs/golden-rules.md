# 황금 원칙

코드를 쓰기 전에 항상 읽는다. 여기 있는 것들은 **개별 판단으로 어기지 않는다** —
어겨야 할 이유가 생겼다면 그건 이 문서를 고쳐야 한다는 신호다.

원칙의 목적은 취향 통일이 아니라 **드리프트 방지**다. 에이전트는 레포에 이미 있는 패턴을
복제하므로, 나쁜 패턴 하나가 들어오면 그 뒤로 계속 번식한다.

## 1. 직접 만든 헬퍼보다 공유 유틸리티를 쓴다

불변 조건을 한 곳에서 관리하기 위해서다. 같은 일을 하는 함수를 각자 만들면
고칠 때 전부 찾아다녀야 한다.

- 프론트 공용 유틸: `apps/web/lib/utils.ts`
- 프론트·백 공유 타입: `packages/types`
- 이미 있는지 먼저 찾는다. 없으면 위 두 곳 중 맞는 자리에 만든다.

## 2. 경계에서 데이터를 파싱한다

**"YOLO-style"로 응답을 더듬지 않는다.** 형태를 추측한 채로 `data.foo.bar`를 쓰면,
런타임에 터지고 원인은 한참 떨어진 곳에서 발견된다.

파싱해야 하는 경계:

| 경계 | 대상 |
|---|---|
| API 응답 | `apps/web`이 `apps/api`에서 받는 모든 것 |
| 요청 바디 | `apps/api`가 받는 모든 것 |
| 폼 입력 | 사용자가 넣는 모든 것 |
| 환경변수 | `process.env.*` |

**라이브러리는 지정하지 않는다.** 파싱한다는 사실만 강제한다.
타입 단언(`as`)으로 때우는 것은 파싱이 아니다.

## 3. 색·간격·radius는 토큰으로만 쓴다

컴포넌트 파일에 hex 값을 하드코딩하지 않는다. 전부 `apps/web/app/globals.css`의
토큰을 거친다. 값 자체와 사용 규칙은 [design-system.md](design-system.md)에 있다.

토큰에 없는 값이 필요하면 임의로 만들지 말고, 토큰을 먼저 추가하고 문서에 적는다.

## 4. 성분 규칙은 개별 성분이 아니라 기능군 단위로 건다

브랜드마다 세부 성분명이 달라서, 개별 성분으로 규칙을 걸면 성분이 추가될 때마다
규칙을 다시 써야 한다. `IngredientGroup` 계층에 걸면 새 성분은 기능군만 지정하면 된다.

배경은 [architecture.md](architecture.md), 성분 근거는
[functional-ingredients.md](functional-ingredients.md).

## 5. 기존 결정을 뒤집기 전에 배경을 읽는다

`docs/architecture.md`의 "왜 이렇게 결정했나"에 이미 검토된 것들이 있다
(다크모드 미지원, 390px 고정, Pretendard self-host, shadcn 최소 도입 등).

같은 논의를 다시 하지 않는다. 뒤집어야 한다면 **그 항목을 갱신하면서** 뒤집는다.

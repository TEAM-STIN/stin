# STIN 요구사항 정의서

피부타입·피부고민 기반 스킨케어 루틴 추천 서비스 STIN의 기능 요구사항을 정의한다.
데이터 모델은 [`apps/api/prisma/schema.prisma`](../apps/api/prisma/schema.prisma),
성분 근거는 [`docs/functional-ingredients.md`](./functional-ingredients.md),
아키텍처 결정은 [`docs/architecture.md`](./architecture.md)를 참조한다.

- 작성일: 2026-09-10
- 최종 수정: 2026-09-10 (인증 방식 소셜 전용으로 변경, 리뷰 추천·정렬 요구사항 추가)
- 상태: 초안 (§10 미확정 항목 확정 후 확정본으로 승격)

## 1. 서비스 개요

### 1.1 해결하려는 문제

스킨케어 정보는 많지만, "내 피부타입에 맞는 제품을 **어떤 순서로 몇 개나** 쓸 것인가"를
알려주는 서비스는 드물다. 특히 개별 제품 추천은 흔한 반면, 여러 제품을 함께 쓸 때 생기는
**성분 병용 문제**(예: 레티놀 + AHA 동시 사용)를 검증해주는 곳은 거의 없다.

### 1.2 핵심 차별점

1. **제품이 아니라 루틴을 추천한다.** 단계 구성(2/3/4단계)과 아침·저녁 시간대까지 포함한 완성된 조합을 제시.
2. **성분 병용 규칙을 사전 검증한다.** 추천 결과가 나오기 전에 조합 자체를 검사하고, 충돌은 시간대 분리로 해소한다.
3. **추천 근거를 문장으로 보여준다.** 각 제품이 왜 뽑혔는지 성분 데이터에서 생성한 한 문장을 제시.
4. **리뷰에 작성자 피부타입을 붙인다.** 같은 피부타입 사용자의 평가를 골라 볼 수 있다.

### 1.3 사용 맥락

모바일 전용(390px 고정). "세면대 앞에서 폰으로 오늘 루틴 확인" 시나리오를 전제한다.
데스크톱 레이아웃은 설계하지 않는다([architecture.md](./architecture.md) 참조).

## 2. 용어 정의

| 용어 | 정의 | 스키마 대응 |
|---|---|---|
| 피부타입 | 사용자가 온보딩에서 선택하는 5종 중 1개 (단일 선택) | `SkinType` |
| 피부고민 태그 | 사용자가 선택하는 7종 중 N개 (복수 선택) | `ConcernTag` |
| 단계 수 | 루틴을 구성하는 제품 개수 (2/3/4) | `RoutineTemplate.stepCount` |
| 루틴 템플릿 | 단계 수별 고정 단계 구성(순서 + 카테고리) | `RoutineTemplate` / `RoutineTemplateStep` |
| 시간대 | 아침(AM) / 저녁(PM) | `TimeOfDay` |
| 성분 그룹 | 병용 규칙·고민 매핑이 갈리는 최소 단위 (예: `AHA류`) | `IngredientGroup` |
| 병용 규칙 | 두 성분 그룹을 같이 쓸 수 있는지에 대한 규칙 | `IngredientRule` |
| 고민 매핑 | 한 성분 그룹이 특정 고민에 도움/부적합인지 | `IngredientGroupConcern` |
| 추천 근거 | 제품이 왜 추천됐는지 설명하는 한 문장 | `RoutineStep.reasonText` |
| 저장된 루틴 | 사용자가 계정에 보관한 추천 결과 스냅샷 | `Routine` / `RoutineStep` |
| 리뷰 추천 | 다른 사용자의 리뷰가 도움이 됐다고 표시하는 행위. 정렬 기준이 된다 | `ReviewRecommendation` `[스키마 변경]` |

## 3. 사용자 유형 및 권한

로그인하지 않은 사용자도 서비스의 핵심 가치(루틴 추천)를 끝까지 경험할 수 있어야 한다.
쓰기 동작(저장·리뷰 작성·추천)과 **리뷰 전체 열람**은 로그인을 요구한다.

| 기능 | 비로그인 | 로그인 |
|---|:---:|:---:|
| 온보딩 (피부타입·고민·단계 입력) | O | O |
| 루틴 추천 결과 조회 | O | O |
| 추천 근거 조회 | O | O |
| 제품 상세 조회 | O | O |
| 제품 평가 요약 (총 리뷰 수, 좋아요 비율) 조회 | O | O |
| 리뷰 열람 | **△ 추천순 1건만** | O (전체) |
| 리뷰 추천(도움돼요) | X | O |
| 제품 교체 및 재분석 | X | O |
| 루틴 저장 / 저장된 루틴 조회 | X | O |
| 리뷰 작성·수정·삭제 | X | O |

리뷰 열람 제한은 로그인 유도 장치다. 상세 규칙은 FR-REV-09 참조.

> 비로그인 사용자의 온보딩 입력값은 서버에 저장하지 않고 클라이언트 세션(브라우저 상태)에만
> 유지한다. 로그인 후에는 `User.skinType` / `User.concernTags`에 저장한다. `[구현됨]`

## 4. 기준 데이터

### 4.1 피부타입 (5종, 단일 선택) `[구현됨]`

| 값 | 표기 |
|---|---|
| `OILY` | 지성 |
| `DRY` | 건성 |
| `COMBINATION` | 복합성 |
| `DEHYDRATED_OILY` | 수부지 |
| `NORMAL` | 중성 |

### 4.2 피부고민 태그 (7종, 복수 선택) `[구현됨]`

| 값 | 표기 |
|---|---|
| `TROUBLE` | 트러블 |
| `KERATIN` | 각질 |
| `PORE` | 모공 |
| `REDNESS` | 홍조 |
| `SENSITIVE` | 민감 |
| `WRINKLE` | 주름 |
| `PIGMENTATION` | 색소침착 |

> 초기 기획은 5종(트러블·각질·모공·홍조·민감)이었으나, 스키마·시드·성분 문서가 이미 7종
> 기준으로 작성되어 있어 **7종으로 확정**한다. 주름·색소침착의 성분 매핑도 시드에 포함되어 있다.

### 4.3 루틴 단계 구성 (3종)

| 단계 수 | 구성 | 비고 |
|---|---|---|
| 2단계 | 토너 → 크림 | 최소 구성 |
| 3단계 | 토너 → 세럼 → 크림 | 기본 구성 |
| 4단계 | 토너 → 가벼운 세럼 → 고농축 세럼 → 크림 | 세럼 2종은 `RoutineTemplateStep.label`로 구분. **현재 시드는 label 미설정** |

- 단계 구성은 **고정**이다. 사용자가 단계 순서나 카테고리를 바꿀 수 없다.
- 클렌저는 루틴 단계에 **포함하지 않는다.**
- 자외선 차단제도 루틴 단계에 **포함하지 않고**, 모든 고민 공통 정적 안내 문구로만 노출한다.
  (`StepCategory.SUNSCREEN`, `Routine.includeSunscreen`은 향후 확장용으로 스키마에 남아 있으나 현재 미사용)

### 4.4 시간대 (2종)

아침(`AM`)·저녁(`PM`) 루틴을 각각 추천한다. 두 루틴은 **같은 단계 구성**을 공유하되
단계별 제품은 다를 수 있다.

### 4.5 리뷰 입력 항목 `[구현됨]`

**사용기간 (4구간, 단일 선택)** — 스키마 정의대로 확정한다.

| 값 | 표기 |
|---|---|
| `UNDER_1_WEEK` | 1주 미만 |
| `ONE_TO_4_WEEKS` | 1주~4주 |
| `ONE_TO_3_MONTHS` | 1~3개월 |
| `OVER_3_MONTHS` | 3개월 이상 |

> 초기 기획은 3구간(1주 / 1주~1달 / 1달 이상)이었으나, 스킨케어 제품은 효과 판단에 통상
> 4~12주가 걸려 "1달 이상"을 하나로 묶으면 정보량이 줄어든다. 4구간으로 확정.

**아쉬웠던 이유 태그 (4종, 복수 선택)**

| 값 | 표기 |
|---|---|
| `IRRITATION` | 자극 |
| `GREASY` | 유분 |
| `SCENT` | 향 |
| `PRICE` | 가격 |

## 5. 기능 요구사항

### 5.1 계정 / 인증 (AUTH)

**인증은 소셜 로그인만 제공한다.** 이메일·비밀번호 자체 회원가입은 지원하지 않는다.
현재 스키마(`User.email` + `User.passwordHash`)는 자체 로그인 전제라 마이그레이션이 필요하다. §10-2 참조.

| ID | 요구사항 | 우선순위 | 비고 |
|---|---|---|---|
| FR-AUTH-01 | 소셜 제공자 계정으로 로그인한다. 별도의 회원가입 절차 없이 첫 로그인 시 계정이 생성된다. | 필수 | **`[스키마 변경]`** — §10-2 |
| FR-AUTH-02 | 이메일·비밀번호 입력 화면을 제공하지 않는다. 비밀번호를 저장·전송·로깅하지 않는다. | 필수 | `passwordHash` 컬럼 제거 |
| FR-AUTH-03 | 소셜 인증 성공 시 서비스 자체 JWT를 발급해 이후 요청 인증에 사용한다. 제공자 액세스 토큰은 클라이언트에 저장하지 않는다. | 필수 | |
| FR-AUTH-04 | `(제공자, 제공자 계정 ID)` 조합으로 사용자를 식별한다. 같은 조합으로 재로그인하면 기존 계정에 연결된다. | 필수 | `@@unique([provider, providerId])` |
| FR-AUTH-05 | 닉네임·프로필 이미지는 제공자에서 받아 초기값으로 채운다. 제공자가 값을 주지 않으면 기본 닉네임을 생성한다. | 필수 | `User.nickname` `[구현됨]` |
| FR-AUTH-06 | 첫 로그인 사용자는 온보딩으로, 온보딩을 마친 사용자는 원래 화면으로 보낸다. | 필수 | `User.skinType`의 null 여부로 판별 |
| FR-AUTH-07 | 로그인이 필요한 동작을 비로그인 상태로 시도하면 로그인 화면으로 유도하고, 로그인 후 원래 동작으로 복귀한다. | 필수 | 리뷰 열람 제한(FR-REV-09) 포함 |
| FR-AUTH-08 | 로그아웃할 수 있다. | 필수 | |
| FR-AUTH-09 | 회원 탈퇴 시 계정과 개인 데이터(저장 루틴·리뷰)를 처리한다. | 선택 | 삭제/익명화 정책 `[확정 필요]` |
| FR-AUTH-10 | 제공자를 2개 이상 지원하는 경우, 같은 사람이 서로 다른 제공자로 로그인하면 별개 계정으로 취급한다. | 필수 | 계정 통합은 범위 외 |

### 5.3 루틴 추천 (REC)

#### 5.3.1 처리 흐름

```
입력: 피부타입 1개, 고민 태그 N개, 단계 수(2/3/4)

1. RoutineTemplate 조회        → 단계 구성(순서 + 카테고리) 확정
2. 단계별 후보 필터링          → 피부타입 적합 + AVOID 성분 배제
3. 후보 점수화                 → 고민 태그 ∩ HELPS 매핑의 weight 합산
4. AM/PM 조합 생성
5. 성분 병용 규칙 검증          → IngredientRule (BLOCK / WARN)
6. 트레이드오프 처리            → 시간대 분리 또는 조건 완화로 해소
7. 추천 근거 문장 생성
출력: AM 루틴 + PM 루틴 (각각 N단계) + 단계별 근거 문장
```

#### 5.3.2 요구사항

| ID | 요구사항 | 우선순위 | 비고 |
|---|---|---|---|
| FR-REC-01 | 피부타입·고민 태그·단계 수를 입력받아 **아침 루틴과 저녁 루틴을 각각** 생성한다. | 필수 | |
| FR-REC-02 | 단계별 후보는 `Product.category`가 해당 단계와 일치하고 `suitableSkinTypes`에 사용자 피부타입을 포함하는 제품으로 한정한다. | 필수 | `[구현됨]` |
| FR-REC-03 | 사용자 고민 태그에 대해 `effect=AVOID`로 매핑된 성분 그룹을 포함한 제품은 후보에서 제외한다. | 필수 | `IngredientGroupConcern` `[구현됨]` |
| FR-REC-04 | 후보 점수는 사용자 고민 태그와 겹치는 `effect=HELPS` 매핑의 `weight` 합으로 산출한다. (핵심 100 / 보조 60 / 병행 25) | 필수 | `[구현됨]` |
| FR-REC-05 | 추천 조합은 `IngredientRule` 검증을 통과해야 한다. `BLOCK` 위반 조합은 폐기하고, `WARN`은 트레이드오프 처리 대상으로 넘긴다. | 필수 | `[구현됨]` |
| FR-REC-06 | `WARN` 충돌은 두 성분을 **서로 다른 시간대로 분리**해 해소하는 것을 1순위로 시도한다. 분리로 해소되지 않으면 점수가 낮은 쪽 제품을 교체한다. | 필수 | |
| FR-REC-07 | 아침 루틴은 **자극성·광과민성 성분을 최소화**한다. 해당 성분 그룹(레티노이드류, 고농도 비타민C, AHA류/BHA류 등)은 저녁 루틴에 우선 배치한다. | 필수 | **`[스키마 변경]`** — §10-1 참조 |
| FR-REC-08 | 저녁 루틴은 고민 태그에 대한 `HELPS` 성분을 가장 효과적으로 배치한다. 세럼 단계에 고득점 기능성 제품을 우선한다. | 필수 | |

## 7. 데이터 요구사항

### 7.1 기준 데이터 준비 현황

| 데이터 | 현황 | 비고 |
|---|---|---|
| 성분 그룹 | 11개 시드 완료 | 보습·항산화·펩타이드·미백 보조 그룹 미반영 |
| 성분 병용 규칙 | 8건 시드 완료 | `BLOCK` 2건 / `WARN` 6건 |
| 성분-고민 매핑 | 40여 건 시드 완료 | 7개 고민 전체 커버 |
| 루틴 템플릿 | 3건 시드 완료 | 2/3/4단계 + `recommendedSkinTypes`. 단, 4단계의 세럼 2개에 `label`이 비어 있어 '가벼운/고농축' 구분이 데이터에 없음 |
| 브랜드 / 제품 / 전성분 | **미준비** | 추천이 동작하려면 필수. §10-3 |

### 7.2 집계 데이터

**제품 평가 요약** (총 리뷰 수, 좋아요 비율)은 별도 캐시 컬럼 없이 `Review` 집계 쿼리로 계산한다.
리뷰 수가 늘어 성능 문제가 생기면 `Product`에 집계 컬럼을 추가한다 `[스키마 변경]`.

**리뷰 추천 수**는 기본 정렬 기준(FR-REV-12)이라 목록 조회마다 필요하다. 초기에는
`ReviewRecommendation` 집계로 처리하되, 정렬 성능이 문제가 되면 `Review.recommendCount`
비정규화 컬럼을 두고 추천/취소 시 트랜잭션으로 함께 갱신한다 `[스키마 변경]`.

## 9. 범위 외 (Out of Scope)

1차 릴리스에서 다루지 않는다.

- 클렌저·자외선 차단제의 루틴 단계 편입 (스키마에 자리만 남겨둠)
- 제품 구매 연동, 가격 비교, 외부 커머스 링크
- 사용자가 DB에 없는 제품을 직접 등록하는 기능
- 이메일·비밀번호 자체 회원가입, 비밀번호 찾기
- 서로 다른 소셜 제공자 계정 간 통합
- 루틴 사용 기록·알림·트래킹 (오늘 루틴 체크 등)
- 사진 기반 피부 진단
- 데스크톱 전용 레이아웃, 다크모드
- 리뷰 신고·모더레이션 운영 도구
- 다국어

## 10. 미확정 사항

확정되어야 구현에 들어갈 수 있는 항목.

### 10-1. 아침/저녁 배치 기준을 데이터로 표현할 방법 `[스키마 변경]` — 우선순위 높음

FR-REC-07("아침 루틴은 자극성·광과민성 성분을 최소화")을 만족하려면 "이 성분 그룹은 저녁에
써야 한다"는 정보가 필요한데, **현재 스키마에는 이를 담을 자리가 없다.**
`IngredientGroupConcern`은 "고민에 맞는가"만, `IngredientRule`은 "같이 써도 되는가"만 표현한다.

선택지:

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| A | `IngredientGroup`에 `preferredTimeOfDay: TimeOfDay?` 추가 | 가장 단순. 시드 11건에 값만 채우면 됨 |
| B | `IngredientGroup`에 `isPhotosensitive` / `isIrritant` Boolean 2개 추가 | 사유가 명확해 근거 문장 생성에 유리. 규칙 로직은 직접 작성 |
| C | 추천 엔진에 성분 그룹명을 하드코딩 | 마이그레이션 불필요하지만 성분 추가 시마다 코드 수정. 기능군 단위 모델링 원칙에 어긋남 |

> 제안: **B안**. "광과민성이라 아침을 피했다"와 "자극이 커서 저녁에 뒀다"는 사용자에게 보여줄
> 근거 문장이 다르고, 민감성 피부에 대한 감점 로직에도 재사용할 수 있다.

### 10-2. 소셜 로그인 전환에 따른 `User` 스키마 변경 `[스키마 변경]` — 우선순위 높음

현재 `User`는 자체 로그인 전제(`email` unique + `passwordHash` 필수)라 소셜 전용 정책과 맞지 않는다.

```prisma
enum AuthProvider {
  KAKAO
  // NAVER / GOOGLE / APPLE — 지원 시 추가
}

model User {
  id              String       @id @default(cuid())
  provider        AuthProvider
  providerId      String       // 제공자가 발급한 고유 ID
  email           String?      // 제공자가 제공하는 경우만. unique 해제
  nickname        String
  profileImageUrl String?
  // passwordHash 제거
  skinType        SkinType?
  concernTags     ConcernTag[]
  createdAt       DateTime     @default(now())

  @@unique([provider, providerId])
}
```

결정할 것:

| 항목 | 선택지 | 제안 |
|---|---|---|
| 지원 제공자 | 카카오 단일 / 카카오+네이버 / +구글·애플 | **카카오 단일로 시작.** 국내 모바일 사용자 커버율이 높고, 제공자마다 콜백·동의항목 처리가 늘어난다 |
| 이메일 수집 | 필수 동의 / 선택 동의 / 수집 안 함 | **수집 안 함.** 이메일을 쓸 기능(알림·비밀번호 재설정)이 범위에 없다 |
| 탈퇴 처리 | 하드 삭제 / 익명화 | **익명화.** 리뷰를 지우면 다른 사용자의 판단 근거가 사라진다 (FR-AUTH-09) |

### 10-3. 리뷰 추천 모델 추가 `[스키마 변경]` — 우선순위 높음

FR-REV-18~22를 위해 추천 기록을 담을 모델이 필요하다. 추천은 정렬 기본값(FR-REV-12)이라
"몇 명이 눌렀는지"뿐 아니라 "내가 눌렀는지"(FR-REV-21)도 알아야 하므로 카운터만으로는 부족하다.

```prisma
model ReviewRecommendation {
  id        String   @id @default(cuid())
  reviewId  String
  review    Review   @relation(fields: [reviewId], references: [id], onDelete: Cascade)
  userId    String
  user      User     @relation(fields: [userId], references: [id])
  createdAt DateTime @default(now())

  @@unique([reviewId, userId])
  @@index([reviewId])
}
```

- 리뷰 삭제 시 추천도 함께 삭제한다(`onDelete: Cascade`).
- 본인 리뷰 추천 차단(FR-REV-20)은 DB 제약으로 표현할 수 없어 **서비스 레이어에서 검증**한다.
- 정렬 성능이 문제가 되면 §7.2의 `Review.recommendCount` 비정규화를 도입한다.

### 10-4. 제품 데이터 확보 방안 — 우선순위 높음

추천 엔진이 동작하려면 제품 + 전성분 데이터가 필요하다. 현재 0건.
수집 방법(수기 입력 / 공개 데이터 / 크롤링), 초기 목표 건수, 카테고리별 최소 확보량을 정해야 한다.
성분 그룹 매칭이 되려면 전성분 중 **최소한 시드된 11개 그룹 소속 성분**은 정확히 입력돼야 한다.

### 10-5. 그 외

| 항목 | 내용 | 제안 |
|---|---|---|
| 고민 태그 최대 선택 수 | 7개를 모두 고르면 AVOID 필터가 겹쳐 후보가 0이 될 수 있다 | 최대 3개 |
| 추천 동점 처리 | 점수가 같은 제품 간 우선순위 | 리뷰 좋아요 비율 → 가격 낮은 순 |
| 근거 수준 노출 | `EvidenceLevel`을 사용자에게 보여줄지 | 뱃지로 노출 (신뢰도 차별점) |
| 저장 루틴 개수 상한 | | 10개 |
| 재구매 의향 필수 여부 | 스키마는 nullable | 필수 입력 |
| 리뷰 목록 페이지 크기 | 무한 스크롤 1회 로드 건수 | 10건 |
| 추천 어뷰징 대응 | 다계정 추천 몰아주기 | 1차 범위 외. 계정당 1회 제약으로만 방어 |
| 추천순 노출 안정성 | 신규 리뷰는 추천 0이라 영원히 하단에 머문다 | 1차는 단순 추천순 유지. 필요 시 최신 리뷰 일부를 상단에 섞는 방식 검토 |
| 4단계 세럼 label | 시드에 `label`이 없어 '가벼운 세럼/고농축 세럼'을 구분할 수 없다 | 시드에 label 채우고, 세럼 단계 후보 필터에 반영 |
| 비로그인 결과 공유 | 추천 결과를 URL로 공유할지 | 1차 범위 외 |

# 아키텍처 및 의사결정 기록

작업하면서 결정한 것들을 그때그때 여기 채워나간다. README를 나중에 몰아 쓰는 대신,
이 파일을 먼저 채우고 README는 여기서 뽑아 정리하는 순서를 권장.

## 시스템 구성

```
[브라우저]
     │ HTTPS
     ▼
┌──────────────── AWS EC2 ────────────────┐
│  Nginx  ─┬─ /      → Next.js  (:3000)   │
│          └─ /api   → NestJS   (:3001)   │
│                          │               │
│                          ▼               │
│                    PostgreSQL (컨테이너) │
└───────────────────────────────────────────┘
```

## 왜 이렇게 결정했나

### 왜 schema.prisma에 datasource url을 안 쓰고 prisma.config.ts로 분리했는가
Prisma 7부터 `datasource.url`을 schema.prisma에 직접 쓰는 방식이 제거되어, DB 연결 문자열은 `apps/api/prisma.config.ts`(CLI용)와 런타임의 `@prisma/adapter-pg` 어댑터(NestJS 코드용)로 옮겨야 한다. `apps/api/.env`의 `DATABASE_URL`은 그대로 두 곳에서 공유해서 읽는다.

### 왜 프론트를 모바일 전용 390px 고정으로 뒀는가
디자인 시안이 전부 390px 모바일 화면이었고(시안 파일은 레포에 없다 — 확정된 값은
`docs/design-system.md`에 있다), 서비스 사용 맥락도
"세면대 앞에서 폰으로 루틴 확인"이라 데스크톱 레이아웃을 따로 설계할 이유가 없었다.
반응형 분기를 없애면 화면 7개를 만드는 속도가 빨라진다. 데스크톱에서는 390px 프레임을
중앙 정렬하고 뒤에 backdrop만 깐다.

### 왜 다크모드를 지원하지 않는가
디자인 시안에 다크 팔레트가 없었고, 베이스 `#F4D2E3` / 포인트 `#FF4DC4`가 밝은 톤 전용으로
설계됐다. 다크 팔레트를 새로 만드는 건 학습 목표와 무관한 추가 작업이라 범위에서 뺐다.

### 왜 시스템 폰트 대신 Pretendard를 self-host 하는가
원래 시안은 시스템 폰트 스택이지만, EC2에 CDN 없이 배포하는 구성에서 OS·브라우저마다
한글 렌더링이 갈리는 걸 막으려고 `PretendardVariable.woff2`(SIL OFL-1.1)를 레포에 넣고
`next/font/local`로 로드한다. 폰트 파일 ~2MB는 감수. 동적 서브셋 최적화는 후속 과제.

### 왜 shadcn을 쓰되 컴포넌트는 최소만 가져오는가
Radix 프리미티브 위에 스타일이 얹힌 코드를 복사해오는 방식이라 라이브러리 종속이 없고,
접근성(포커스 트랩·키보드)이 어려운 것만 골라 쓸 수 있다. 화면에 실제로 필요한
컴포넌트만 PR로 추가한다. 상세 규칙은 `docs/design-system.md`.

### 왜 리뷰 추천을 카운터 컬럼이 아니라 기록 테이블(ReviewRecommendation)로 뒀는가
추천순이 리뷰 목록의 기본 정렬(FR-REV-12)이라 추천 수가 필요하지만, 버튼 상태를 그리려면
"내가 이 리뷰를 추천했는지"(FR-REV-21)와 중복 추천 방지·토글(FR-REV-19)도 알아야 한다.
`Review.recommendCount` 하나로는 둘 다 표현할 수 없어 `(reviewId, userId)` unique 기록 테이블로 뒀다.
추천 수는 집계로 구하고, 정렬 성능이 문제될 때만 카운터를 비정규화해 추가한다.
리뷰가 삭제되면 추천도 의미가 없어 `onDelete: Cascade`. 본인 리뷰 추천 금지(FR-REV-20)는
두 테이블에 걸친 조건이라 DB 제약으로 걸 수 없어 서비스 레이어에서 검증한다.

### 왜 사용자를 이메일이 아니라 (provider, providerId)로 식별하는가
인증을 소셜 로그인만 제공하기로 하면서(FR-AUTH-01·02) 비밀번호 컬럼을 없앴다. 이메일은 카카오에서
선택 동의 항목이라 없을 수 있고, 제공자를 늘리면 같은 이메일이 서로 다른 계정에 나타날 수 있어
식별자로 쓸 수 없다. 제공자가 발급한 계정 ID는 항상 있고 제공자 안에서 유일하므로
`@@unique([provider, providerId])`로 식별한다(FR-AUTH-04). 제공자가 달라지면 별개 계정이다(FR-AUTH-10).
제공자는 카카오 하나로 시작한다 — 국내 모바일 사용자 커버율이 높고, 제공자마다 콜백·동의항목 처리가 늘어난다.
결정 과정은 `docs/requirements.md` §10-2.

### 왜 탈퇴한 사용자를 삭제하지 않고 익명화하는가
리뷰는 같은 피부타입 사용자의 판단 근거라 탈퇴와 함께 사라지면 안 되고(§10-2), 추천순 정렬도 탈퇴 때문에
흔들리지 않아야 한다. 사용자 행을 지우고 `Review.userId`를 null로 두는 방식도 있었지만, 그러면 리뷰·추천을
읽는 모든 쿼리가 작성자 없음을 따로 처리해야 한다. 그래서 행은 남기고 `deletedAt`을 기록한 뒤 식별 가능한
값(제공자 계정 ID·이메일·프로필 이미지·피부 정보)을 비우고 닉네임을 `탈퇴한 사용자`로 바꾼다.
`providerId`를 비우는 이유는 같은 카카오 계정으로 다시 가입했을 때 옛 계정에 연결되지 않고 새 계정이 되게 하려는 것.
Postgres unique는 null끼리 충돌하지 않아 `(provider, providerId)` 제약을 그대로 쓸 수 있다.
저장 루틴은 본인만 보는 데이터라 탈퇴 시 삭제한다. 절차는 `docs/requirements.md` §10-2.

## 추천 엔진 처리 흐름

```
1. RoutineTemplate 조회 → 단계 구성 + 시간대
2. 단계별 후보 필터링 (피부타입 · 고민 태그 일치)
3. 조합 생성
4. 성분 병용 규칙 검증 (IngredientRule, BLOCK/WARN)
5. 트레이드오프 처리 (해가 없으면 우선순위대로 조건 완화,
   또는 아침/저녁 분리로 해소 시도)
6. 추천 근거 문장 생성
```
